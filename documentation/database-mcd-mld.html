1. Contexte & sources

Ce document formalise la structure de la base de données avant le développement des modules Auth (#1, #2, #3) et Tickets (#6, #7). Il suit la méthode Merise : règles de gestion → dictionnaire des données → MCD (Modèle Conceptuel de Données) → MLD (Modèle Logique de Données) → script DDL PostgreSQL.

Exigences du cahier des charges prises en compte :

  • §1 Tickets — titre, description, priorité (basse/moyenne/haute/critique), statut (ouvert/en cours/résolu/fermé), date de création, date de résolution.
  • §2 Assignation — assigner / réassigner un ticket à un technicien.
  • §3 Filtrage & tri — par statut, priorité, technicien ; recherche textuelle titre + description.
  • §4 Rôles — utilisateur standard, technicien, admin (RBAC).
  • §5 Dashboard — temps moyen de résolution, répartition par priorité/statut.
  • Bonus #11 — commentaires sur les tickets (auteur, timestamp, contenu).

2. Règles de gestion

  • RG1 — Un utilisateur possède un et un seul rôle (standard, technicien ou admin). Un rôle peut être attribué à plusieurs utilisateurs.
  • RG2 — Un ticket est créé par un et un seul utilisateur. Un utilisateur peut créer zéro ou plusieurs tickets.
  • RG3 — Un ticket peut être assigné à au plus un technicien à la fois (assignation optionnelle à la création). Un technicien peut avoir zéro ou plusieurs tickets assignés.
  • RG4 — La réassignation remplace l'assigné courant (l'historique complet est une extension — voir §8).
  • RG5 — Un ticket passe par les statuts : ouvert → en_cours → resolu → ferme. La date de résolution (resolved_at) n'est renseignée qu'au passage en resolu.
  • RG6 — Un commentaire est écrit par un et un seul utilisateur et concerne un et un seul ticket (bonus #11).
  • RG7 — L'email d'un utilisateur est unique ; le mot de passe est stocké uniquement sous forme de hash (bcrypt) — jamais en clair.

4. MCD — Modèle Conceptuel de Données

Entité Relation Cardinalité (min,max) PK = clé primaire   FK = clé étrangère

Lecture des cardinalités

RelationCôté UTILISATEURCôté autre entitéSignification
possède(1,1)(0,n) côté ROLEUn utilisateur a exactement 1 rôle ; un rôle peut concerner 0 à n utilisateurs.
crée(0,n)(1,1) côté TICKETUn utilisateur peut créer 0 à n tickets ; un ticket a exactement 1 créateur.
est assigné à(0,n)(0,1) côté TICKETUn technicien peut avoir 0 à n tickets ; un ticket a au plus 1 assigné (optionnel).
écrit(0,n)(1,1) côté COMMENTAIREUn utilisateur peut écrire 0 à n commentaires ; un commentaire a 1 seul auteur.
concerne(0,n) côté TICKET / (1,1) côté COMMENTAIREUn ticket peut avoir 0 à n commentaires ; un commentaire concerne 1 seul ticket.

5. MLD — Modèle Logique de Données (relationnel)

Passage au relationnel : chaque entité devient une table ; les relations (x,1)/(1,1) se traduisent par des clés étrangères.

5.1 Schéma textuel

roles (id, name, description, created_at)
users (id, name, email, password_hash, created_at, updated_at, #role_id → roles.id)
tickets (id, title, description, priority, status, created_at, resolved_at, updated_at, #creator_id → users.id, #assignee_id → users.id)
comments (id, content, created_at, #ticket_id → tickets.id, #author_id → users.id)

Choix de conception : les rôles sont une table (et pas un enum) pour supporter le RBAC (#2) et l'ajout futur de permissions sans migration. En revanche priority et status sont des VARCHAR + CHECK (listes figées par le cahier des charges) — plus simples qu'un type ENUM PostgreSQL, qui est difficile à faire évoluer.

6. Script DDL PostgreSQL

Script de création complet (base des futures migrations — ticket #1 / setup BDD) :

-- ============================================================
-- TaskForge — Schéma PostgreSQL (v1.0)
-- Ordre de création : roles → users → tickets → comments
-- ============================================================

CREATE TABLE roles (
  id          SERIAL       PRIMARY KEY,
  name        VARCHAR(50)  NOT NULL UNIQUE,
  description TEXT,
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- Rôles imposés par le cahier des charges (§4)
INSERT INTO roles (name, description) VALUES
  ('utilisateur', 'Crée des tickets et suit leur avancement'),
  ('technicien',  'Résout les tickets qui lui sont assignés'),
  ('admin',       'Gère tout : utilisateurs, tickets, configuration');

CREATE TABLE users (
  id            SERIAL       PRIMARY KEY,
  name          VARCHAR(100) NOT NULL,
  email         VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,  -- bcrypt, jamais en clair (RG7)
  role_id       INTEGER      NOT NULL REFERENCES roles(id),
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ
);

CREATE TABLE tickets (
  id          SERIAL       PRIMARY KEY,
  title       VARCHAR(200) NOT NULL,
  description TEXT         NOT NULL,
  priority    VARCHAR(10)  NOT NULL CHECK (priority IN
                ('basse', 'moyenne', 'haute', 'critique')),
  status      VARCHAR(15)  NOT NULL DEFAULT 'ouvert' CHECK (status IN
                ('ouvert', 'en_cours', 'resolu', 'ferme')),
  creator_id  INTEGER      NOT NULL REFERENCES users(id),
  assignee_id INTEGER      REFERENCES users(id) ON DELETE SET NULL,
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
  resolved_at TIMESTAMPTZ,  -- renseigné au passage en 'resolu' (RG5)
  updated_at  TIMESTAMPTZ
);

CREATE TABLE comments (  -- Bonus #11
  id         SERIAL      PRIMARY KEY,
  ticket_id  INTEGER     NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  author_id  INTEGER     NOT NULL REFERENCES users(id),
  content    TEXT        NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ============ INDEX (filtrage / tri / recherche — §3 du CDC) ============
CREATE INDEX idx_tickets_status    ON tickets (status);
CREATE INDEX idx_tickets_priority  ON tickets (priority);
CREATE INDEX idx_tickets_assignee  ON tickets (assignee_id);
CREATE INDEX idx_tickets_created   ON tickets (created_at DESC);
CREATE INDEX idx_comments_ticket   ON comments (ticket_id);

-- Recherche textuelle titre + description (§3) : trigrammes
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_tickets_search ON tickets
  USING gin ((title || ' ' || description) gin_trgm_ops);

-- ============ TRIGGER updated_at ============
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_users_updated   BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
CREATE TRIGGER trg_tickets_updated BEFORE UPDATE ON tickets
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

7. Requêtes clés (dashboard — §5 du CDC)

-- Temps moyen de résolution (ticket #11)
SELECT AVG(resolved_at - created_at) AS temps_moyen_resolution
FROM tickets
WHERE resolved_at IS NOT NULL;

-- Répartition par statut / priorité
SELECT status,   COUNT(*) FROM tickets GROUP BY status;
SELECT priority, COUNT(*) FROM tickets GROUP BY priority;
RG5 — la validation des transitions de statut (ouvert → en_cours → resolu) sera testée unitairement (§7 du CDC). Le CHECK contraint les valeurs ; la séquence des transitions sera garantie par la couche service backend.
